## Item 1: Instructor Proposal Mismatch

### Problem

The staff portal dashboard shows a "Propose a Class" action for instructor-group staff. The API route `POST /api/staff/classes/create` appears to support proposals. However, `app/staff/(portal)/classes/create/page.tsx` currently **blocks non-management staff from accessing class creation**. The UI and API are contradicting each other.

Effect: an instructor who clicks "Propose a Class" gets blocked. If the block is removed, proposals go to `pending_owner_approval` — but the owner approvals page approves directly to `published` (not `draft` as originally designed), which may skip the owner's editorial review.

### Why It Matters

Staff who have been told they can propose classes cannot do so. The approval chain is unclear: the `POST /api/owner/classes/[id]/approve` route currently sets approved classes to `published` directly, but the `SYSTEM_FLOW.md` says approve → `draft` and then the owner must publish separately. This inconsistency means staff-proposed classes may go live without the owner reviewing and publishing them consciously.

### Recommended Solution

**Decision required:** Choose one of these two options before coding:

- **Option A — Instructor proposals are allowed.** Remove the management-only guard in the class create page. Ensure the API sets status to `pending_owner_approval`. Change the approve route to set status to `draft` (not `published`) so the owner still publishes deliberately. Add an owner approvals count badge/notification to the owner dashboard.

- **Option B — Instructor proposals are not supported yet.** Remove the "Propose a Class" link from the instructor staff dashboard. Keep the management-only guard. Keep the current approve → `published` behavior for management-created classes (which are not pending approval anyway — management can publish directly). Document instructor proposals as a Phase 13/14 feature.

### Files Likely Affected

- `app/staff/(portal)/classes/create/page.tsx` — the management-only guard
- `app/staff/(portal)/dashboard/page.tsx` — the "Propose a Class" link
- `app/api/owner/classes/[id]/approve/route.ts` — approve → published vs approve → draft
- `app/owner/approvals/page.tsx` — owner approval queue
- `VIBEPASS_PROJECT_HANDBOOK.md` — handbook section on staff user groups

### Database / API Changes

- No schema changes needed for Option A or B.
- API behavior change in approve route only if choosing Option A.

### Testing Checklist

- [ ] Login as instructor-group staff.
- [ ] Check whether "Propose a Class" link appears.
- [ ] Click propose — verify access allowed or blocked matches chosen option.
- [ ] If Option A: submit a proposal, check owner sees it in approvals.
- [ ] Owner approves — verify class status is `draft`, not `published`.
- [ ] Owner publishes — verify class appears on marketplace.
- [ ] If Option B: verify "Propose a Class" link is removed from instructor dashboard.

### Priority: P0

### Timing: Must be decided and implemented before launch.

## Item 2: Paid Multi-Attendee Booking Mismatch

### Problem

The booking form supports multiple attendees. The **free booking path** creates one `bookings` row per attendee and calls `increment_booked_count` once per attendee — correct behavior. The **paid booking path** (`POST /api/payments/verify`) creates **one booking for the primary attendee only**, with the total amount. Multiple attendees booking a paid class get only one booking row in the database.

Effect: if a customer books 3 paid seats, only 1 booking row is created, but `booked_count` may increment by 3 (or by 1 — unclear). Owner sees only 1 booking. Customer emails show only 1 attendee. Revenue records are ambiguous (one row with total amount vs. per-attendee breakdown). Seat count may be wrong.

### Why It Matters

This is a data integrity bug. In the worst case, a group that paid for 3 seats appears as 1 booking in the owner's view, customer confirmation emails are wrong, and `booked_count` is off by 2 — allowing overcrowding or showing wrong available seats publicly.

### Recommended Solution

**Option A (correct, more work):** Align the paid path with the free path. After payment verification, create one `bookings` row per attendee. Set all rows with `payment_status = paid`. Link all rows to the same `payments` record. Call `increment_booked_count` once per attendee.

**Option B (simpler interim):** Lock the paid booking form to 1 attendee only. Show a clear UI message: "Paid bookings are currently limited to 1 seat per transaction. For group bookings, contact the studio." Remove the multi-attendee selector when `class.price > 0`. Free classes keep multi-attendee support.

Option B is the faster path to launch safety. Option A is the correct long-term fix.

### Files Likely Affected

- `app/api/payments/verify/route.ts` — creates only one booking currently
- `app/classes/[id]/book/BookingForm.tsx` — attendee count logic and paid path
- `lib/appStore.tsx` — `addBooking` action (free path, already loops per attendee)

### Database / API Changes

- No schema changes for Option B (simpler).
- For Option A: the verify route must loop and insert multiple booking rows, link via a shared payment record, and call `increment_booked_count` N times.

### Testing Checklist

- [ ] Select a paid class.
- [ ] Try to add 2 attendees — check behavior.
- [ ] If Option B: confirm multi-seat selector is hidden/disabled for paid classes.
- [ ] Complete a paid booking for 1 attendee — check `bookings` table has exactly 1 row.
- [ ] Check `payments` table has correct amount.
- [ ] Check `booked_count` incremented by the correct number.
- [ ] Check owner bookings page shows correct count.
- [ ] Check customer receives correct confirmation email.

### Priority: P0

### Timing: Fix before accepting real paid bookings from customers.

## Item 3: Atomic Capacity Enforcement for All Booking Paths

### Problem

The Supabase RPC `increment_booked_count(p_class_id)` is atomic — it prevents overbooking when called correctly. However, there are two booking paths:

1. **Free path**: `addBooking()` in `appStore.tsx` calls the store's Supabase browser client directly. It uses `increment_booked_count` via RPC — good. But the pre-check `if (bookedCount >= capacity) return error` runs **client-side on stale local state**, not as a DB-level lock. Two concurrent free bookings for the last seat could both pass the client-side check before either RPC fires.

2. **Paid path**: `POST /api/payments/verify` runs server-side after payment — the capacity check here should be the authoritative one. But if the check is a simple read before write (not atomic), two payments completing simultaneously could both pass.

The `cancel_booking` RPC decrements correctly, but the combined "check capacity, then insert, then increment" is not wrapped in a transaction.

### Why It Matters

If two customers book the last seat simultaneously, both could succeed. The class would have `booked_count > capacity` — overbooked. Customers would arrive expecting to attend a sold-out class.

### Recommended Solution

Create a new Supabase RPC: `book_if_capacity(p_class_id, p_capacity)` that does the check and increment atomically in a single transaction with a `FOR UPDATE` lock on the class row. Return success/failure. Call this RPC from both the free path (server-side API route, not appStore browser client) and the paid verification route.

This means moving the free booking creation to a server-side API route (`POST /api/bookings/create`) instead of direct browser Supabase writes. This also improves security — currently free bookings bypass the API entirely.

### Files Likely Affected

- `app/classes/[id]/book/BookingForm.tsx` — free path currently calls appStore directly
- `lib/appStore.tsx` — `addBooking` action
- `app/api/payments/verify/route.ts` — paid path capacity check
- A new `app/api/bookings/create/route.ts` — new server-side free booking endpoint
- A new `supabase/book-if-capacity.sql` — atomic RPC

### Database / API Changes

```sql
CREATE OR REPLACE FUNCTION book_if_capacity(p_class_id uuid, p_slots integer DEFAULT 1)
RETURNS boolean LANGUAGE plpgsql AS $$
DECLARE
  current_count integer;
  cap integer;
BEGIN
  SELECT booked_count, capacity INTO current_count, cap
  FROM classes WHERE id = p_class_id FOR UPDATE;

  IF current_count + p_slots > cap THEN
    RETURN false;
  END IF;

  UPDATE classes SET booked_count = booked_count + p_slots WHERE id = p_class_id;
  RETURN true;
END;
$$;
```

### Testing Checklist

- [ ] Two browser tabs — both try to book the last seat at the same time (free class).
- [ ] Verify only one booking succeeds; the other gets a "class is now full" error.
- [ ] Same test with a paid class (harder to test — simulate with server logs).
- [ ] Verify `booked_count` never exceeds `capacity` in the DB.
- [ ] Verify cancellation still correctly decrements `booked_count`.

### Priority: P0

### Timing: Fix before launch if any classes can fill quickly. At minimum, move free booking to server-side route before launch.

It is unclear whether this table exists or whether any admin API routes are currently writing to it. Actions like business approval/rejection/suspension, class hiding, user invitations, and report resolution are high-stakes operations with no trail.

Without audit logs, there is no accountability for admin actions. If a business is wrongly suspended, or a class is hidden incorrectly, there is no record of who did what and when. This is a trust and governance problem — especially critical for a marketplace where owner livelihoods depend on the platform.

3. Call this helper at the end of each admin API route that takes a major action.
4. Add a basic `/admin/audit-logs` page (read-only table, filter by action type and date).

- `business_approved`, `business_rejected`, `business_suspended`, `business_reactivated`, `business_archived`

## Item 5: Refund and Payment Edge Cases

### Problem

The system has several unhandled payment edge cases documented in `SYSTEM_FLOW_UPDATE_PHASE_11.md` but not yet resolved:

**Edge case A — Payment succeeds but booking fails (class fills up after payment):** If `increment_booked_count` returns false (capacity exceeded) after a Razorpay payment has already been captured, the customer loses money. Currently the system does not create a `refund_required` payment status — it creates the booking anyway or fails silently.

**Edge case B — Payment fails but UI shows success:** If Razorpay webhook fires out of order, or verification times out, the booking state may be inconsistent.

**Edge case C — Refund not automated:** When a booking is cancelled (by owner or customer), the payment status should become `refunded` for paid bookings. Currently there is no Razorpay refund API call — the owner must manually process refunds outside the platform. The booking shows `payment_status = paid` even after cancellation.

**Edge case D — Admin has no payment issue queue:** Payments in `refund_required`, `failed`, or disputed states have nowhere to go in the admin portal.

### Why It Matters

Real money is involved. A customer who pays and gets no booking, or who cancels and gets no refund, will dispute the transaction with their bank. This causes chargeback risk and loss of trust.

### Recommended Solution

**Phase A (before launch — P1):**
- Add `refund_required` to the `payment_status` enum.
- If `book_if_capacity` (Item 3) returns false after payment, set payment to `refund_required` and return an error to the user with a support message.
- When a confirmed paid booking is cancelled (owner cancel cascade or customer cancel), automatically set `payment_status = refund_required` and surface it to the admin.
- Add a "Payments needing attention" section to the admin dashboard (a simple count + link).

**Phase B (can be post-launch — P2):**
- Integrate Razorpay Refund API: `POST /api/payments/refund` (server-side, admin-triggered).
- Admin clicks "Issue Refund" on a payment record → Razorpay processes the refund → status becomes `refunded`.

### Files Likely Affected

- `app/api/payments/verify/route.ts` — add refund_required logic
- `app/api/owner/classes/[id]/cancel/route.ts` — update payment status on cancel
- `lib/appStore.tsx` — `cancelBooking` action
- `app/admin/dashboard/page.tsx` — add payment issues count
- `app/admin/payments/page.tsx` — new page (or extend existing admin views)
- `supabase/` — migration to add `refund_required` to enum or update check constraint

### Database / API Changes

```sql
-- Add refund_required status if using a CHECK constraint rather than enum
ALTER TABLE payments DROP CONSTRAINT IF EXISTS payments_status_check;
ALTER TABLE payments ADD CONSTRAINT payments_status_check
  CHECK (status IN ('pending', 'paid', 'failed', 'refunded', 'refund_required', 'partially_refunded'));
```

### Testing Checklist

- [ ] Simulate capacity-full race condition during paid booking → verify payment record has `refund_required`.
- [ ] Cancel a confirmed+paid booking → verify `payment_status` changes to `refund_required`.
- [ ] Admin dashboard shows count of `refund_required` payments.
- [ ] Admin can view list of payments with `refund_required` status.
- [ ] No booking shows `payment_status = paid` after being cancelled (unless intentionally not refunded).

### Priority: P1 (Phase A) / P2 (Phase B with Razorpay Refund API)

### Timing: Phase A before launch. Phase B shortly after.

## Item 6: Admin System Health Page

### Problem

There is no way for an admin to quickly verify that all external integrations and environment dependencies are working correctly. If the Supabase storage bucket is missing, or the Resend API key is wrong, or Razorpay is in test mode when it should be live, the platform silently fails in partial ways that are hard to diagnose.

### Why It Matters

Launch day issues like "bookings are being created but emails aren't sending" or "images aren't uploading" are very common. Without a health check page, the admin must manually test every flow. A health page saves hours of debugging during launch.

Add a new admin page `/admin/health` that runs server-side checks and reports the result of each:

## Item 8: Cross-Portal Status Change Propagation

### Problem

`SYSTEM_FLOW_UPDATE_PHASE_11.md` Section 3 defines the "Critical Cross-Portal Data Linkage Rule" — when data changes in one portal, every dependent area must update. Several known gaps exist:

**Gap A:** When a business is suspended by admin, the admin dashboard stat cards for "active businesses", "published classes", and "platform revenue" should update. But the client-side AppStore data is loaded once at startup and not refreshed — if an admin suspends a business and then opens the analytics page in the same session, stale data may show the suspended business as still active.

**Gap B:** When owner updates a class title or image, the marketplace card, the class detail page, the owner's class list, and the staff dashboard schedule should all show the new data. The AppStore `updateClass` action updates local state, but staff portal pages that read `class_staff` assignments may not pick up the change if they do server-side fetch from a stale session.

**Gap C:** When featured placement is changed by admin (position, label, expiry), the homepage carousel `HomeFeaturedCarousel` component reads from the server-rendered `app/page.tsx` — it should reflect changes on the next page visit. But the admin featured page and the homepage may get out of sync if the admin session's AppStore has stale class data.

**Gap D:** The `featured_until` expiry field exists but there is no scheduled job or trigger to automatically unfeature classes when this date passes. The filter must be applied manually at query time.

### Why It Matters

Stale data in operator tools (owner, admin) causes incorrect decisions. An admin who sees stale revenue numbers might approve or reject a business incorrectly. An owner who sees stale booking counts might overbuild capacity. A customer who sees a stale seat count might attempt to book a sold-out class.

### Recommended Solution

**Short-term (before launch):**
- Ensure all admin API mutations call `router.refresh()` or trigger a store `fetchAll()` on the client after successful response.
- Ensure `HomeFeaturedCarousel` filters out expired featured items at render time using `featured_until < now()`.
- Add a comment/warning to AppStore `fetchAll` that explains caching behavior and how long data may be stale.

**Medium-term (can be post-launch):**
- Add a `featured_until` server-side filter in the featured classes query so expired classes never appear in the carousel.
- Consider Supabase Realtime for the admin dashboard action queue (pending approvals count, open reports count) so it updates without a page refresh.

### Files Likely Affected

- `app/page.tsx` — featured_until filter in server query
- `app/admin/dashboard/page.tsx` — add router.refresh() after mutations
- `lib/appStore.tsx` — consider `fetchAll` re-trigger after admin mutations
- `components/HomeFeaturedCarousel.tsx` — filter expired featured items client-side
- `app/api/admin/classes/[id]/featured/route.ts` — ensure expiry is respected

### Database / API Changes

No schema changes. SQL query filter addition only:

```sql
-- Featured classes query should include:
AND (featured_until IS NULL OR featured_until > now())
```

### Testing Checklist

- [ ] Set a class as featured with an expiry time in the past → verify it does NOT show in homepage carousel.
- [ ] Suspend a business → refresh admin dashboard → verify active business count decreases.
- [ ] Update a class title as owner → visit marketplace → verify new title shows.
- [ ] Admin changes featured position → open homepage in new tab → verify new order.
- [ ] Owner cancels a class → admin analytics → verify GMV decreases (confirmed+paid only).

### Priority: P1

### Timing: The `featured_until` filter is a one-line fix — do before launch. AppStore stale-data warnings are low risk. Realtime is post-launch.

## Item 9: Customer-Facing Copy Toward Experience/Event Discovery

### Problem

Several public-facing strings use the word "class" in technical/administrative contexts where customers would respond better to "experience", "session", or "event". The goal per `SYSTEM_FLOW_UPDATE_PHASE_11.md` Section 23 is: "use 'class/event' or 'event' in UI copy where it improves user experience. Do not rename tables."

Current stale copy examples found in the codebase:
- "Browse and book classes on VibePass" (signup page)
- "class" as a label in booking confirmation emails
- "My Bookings" page header uses "class" in summary cards
- Business public profile page: "Upcoming classes" section header
- Staff dashboard: "Featured class drivers" label in the carousel

### Why It Matters

A young, modern audience (target age 10-30 per the product vision) responds better to language like "Find your next experience", "Discover sessions", or "Book an event" rather than the transactional word "class." This is a positioning and perception issue that affects conversion.

Database tables stay as `classes`. Only UI copy changes.

### Recommended Solution

Do a systematic string audit across all customer-facing pages and components. Replace where appropriate:

| Old | Suggested |
|---|---|
| "Browse classes" | "Explore sessions" or "Discover experiences" |
| "Upcoming classes" (on business page) | "Upcoming sessions" |
| "No classes found" | "Nothing here yet — check back soon!" |
| "Featured class drivers" | "Instructors" or "Who's leading this" |
| "Book a class" | "Book your spot" |

## Item 10: Onboarding Checklists for Owner, Staff, and Admin

### Problem

When a new owner, staff member, or admin logs in for the first time, they face an empty dashboard with no guidance on what to do next. There is no onboarding checklist or first-time flow. This causes:
- Owners creating draft classes but never publishing them (they don't know they need to).
- Staff completing their invite but leaving their profile blank.
- New admins not knowing where to start (approve businesses, set featured classes, configure settings).

The current new-owner experience is: dashboard loads, shows "0 bookings, 0 revenue" — no next step.

### Why It Matters

Onboarding drop-off is one of the highest risk points for marketplace products. If a new owner doesn't create their first class within their first session, they are unlikely to return. An empty marketplace with no active businesses also means no customer bookings — the two sides must be activated together.

### Recommended Solution

Add a progress-style onboarding checklist component that appears at the top of the dashboard only when the user hasn't completed the key setup steps. The checklist dismisses permanently once all steps are done (or can be manually dismissed).

**Owner onboarding checklist:**
1. ✅ Account created
2. Complete your business profile (logo, description, location)
3. Create your first class or session
4. Publish your first class (make it live)
5. Invite your first staff member (optional)
6. Wait for admin approval (if pending)

**Staff onboarding checklist:**
1. ✅ Invite accepted
2. Complete your instructor profile (photo, bio, specialties)
3. Enable your public profile so customers can find you
4. View your assigned upcoming classes

**Admin onboarding checklist (shown once per new admin session):**
1. Review pending business approvals
2. Set featured classes for the homepage
3. Check open reports
4. Verify platform health (links to health page from Item 6)

Completion state can be stored in `localStorage` or as a flag in `profiles` (e.g., `onboarding_dismissed_at`).

### Files Likely Affected

- `components/OnboardingChecklist.tsx` — new reusable component
- `app/owner/dashboard/page.tsx` — show owner checklist
- `app/staff/(portal)/dashboard/page.tsx` — show staff checklist
- `app/admin/dashboard/page.tsx` — show admin checklist (one-time only)
- `types/index.ts` — possibly add `onboardingDismissedAt` to Profile type
- `supabase/` — optional: add `onboarding_dismissed_at` column to profiles

### Database / API Changes

Optional: `ALTER TABLE profiles ADD COLUMN IF NOT EXISTS onboarding_dismissed_at timestamptz;`

Alternatively, use `localStorage` to store dismissal — simpler and avoids a DB change.

### Testing Checklist

## Item 11: Trust/Safety Labels and Report Severity Improvements

### Problem

The `reports` table includes a `severity` field with values `low / medium / high / urgent` — but the admin reports page (`/admin/reports`) may not display or filter by severity. Reports currently have statuses `open / resolved / ignored`, but the Phase 11 spec defined 5 statuses: `open / reviewing / resolved / dismissed / action_taken`.

Additionally, the public report modal (via `ReportButton.tsx`) collects: type, reason, and description — but does not let the reporter indicate severity. Admins have no way to quickly triage which reports need urgent attention.

On the public side, there are no visible trust signals for customers — no verified business badges, no safety labels on profiles, no visible report counts or status on classes/businesses.

### Why It Matters

A marketplace where users can't signal trust or report bad actors will be misused. At launch, at least basic safety signals need to exist. Admin triage without severity visibility means urgent reports get treated the same as minor ones.

### Recommended Solution

**Short-term fixes:**
- Ensure the admin reports page shows and can filter by `severity`.
- Add severity as a field in the `ReportButton` modal (user selects: "I feel unsafe" = urgent, "Wrong information" = low).
- Extend report status to include `reviewing` and `action_taken` in both DB and admin UI.

**Trust labels (simple, no new infrastructure):**
- Add a "Verified" badge to businesses that are `status = active` and have been approved by admin. This is just a UI label — no new DB field needed.
- Add a "Trusted Instructor" display label to staff where `public_profile_visible = true` and the business is active.
- On the admin reports page, show a colored severity pill: green for low, yellow for medium, orange for high, red for urgent.

### Files Likely Affected

- `components/ReportButton.tsx` — add severity selector
- `app/admin/reports/page.tsx` — show severity, add status filter for reviewing/action_taken
- `app/api/reports/route.ts` — accept severity in payload
- `app/businesses/[id]/page.tsx` — show "Verified" badge
- `app/staff/[id]/page.tsx` — show "Trusted Instructor" if eligible
- `components/ClassCard.tsx` — optionally show verified business badge
- `supabase/` — update report status check constraint

### Database / API Changes

```sql
-- Update reports status constraint to include new statuses
ALTER TABLE reports DROP CONSTRAINT IF EXISTS reports_status_check;
ALTER TABLE reports ADD CONSTRAINT reports_status_check
  CHECK (status IN ('open', 'reviewing', 'resolved', 'dismissed', 'action_taken'));
```

- [ ] Staff with public profile shows "Trusted Instructor" badge on their profile page.

### Priority: P2

### Timing: Severity display and status fix are quick — do before launch. Trust badges are polish — do during soft launch.

## Item 12: Future Roadmap Items (Post-Launch Documentation)

### Problem

Several features were identified in the product vision and system flow documents as important for the platform's long-term success, but they do not belong in the pre-launch hardening work. They need to be clearly documented so they don't accidentally get built prematurely, and so the team has a shared roadmap.

### Roadmap Items for Phase 14 and Beyond

**Favorites / Saved Classes**
- Customer can save a class or business to a favorites list.
- No code built yet. Add as Phase 14 item.
- DB: `favorites` table with `customer_id`, `entity_type`, `entity_id`.

**Waitlist**
- When a class is sold out, customer can join a waitlist.
- If a booking is cancelled, the next person on the waitlist gets an invite.
- Requires: `waitlist` table, a trigger or scheduled job to process waitlist on cancellation, notification email.
- Add as Phase 14 item.

**Support Tickets / Customer Help**
- Customer or owner can open a support ticket (different from reports — not about content moderation, but about billing, access, or account issues).
- Currently there is no way for a customer or owner to contact support through the platform.
- Add as Phase 14 item.

**Owner Payouts**
- Currently the platform tracks GMV and platform margin, but there is no mechanism to pay owners their share (GMV minus platform margin). 
- Razorpay supports marketplace payouts/route — this would require account configuration and compliance.
- Add as Phase 14 item. Owner should be clearly told in the UI that payouts are not yet automated.

**Reviews and Ratings**
- Customers can rate a class after attending.
- Average rating shown on class detail and business profile.
- DB: `reviews` table with `booking_id`, `rating`, `comment`, `created_at`.
- Add as Phase 14 item.

**Memberships and Passes**
- Customers buy a membership or class pass for unlimited or N bookings per month.
- Complex billing integration required.
- Add as Phase 14 item.

**SMS / WhatsApp Notifications**
- Currently email only. SMS/WhatsApp via Twilio or MSG91 adds significant reach for the 10-30 age group.
- Add as Phase 14 item.
